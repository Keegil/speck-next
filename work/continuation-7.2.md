# Continuing unfinished work — 7.2

The owner requested a method repair after repeated local fixes failed to produce a coherent product experience, then authorized a direct release and upgrades of relevant projects. The observed pattern was an old next command becoming the work's destination. Concrete private product evidence stays in its product repository.

## Change

The root method now gives builders a short continuation procedure: preserve the current request and constraints, identify the remaining obstacle to the complete job, and choose the authorized action that addresses it. Supporting work names its consumer. Repeated repairs of the same failing job prompt an examination of the shared mechanism and work boundaries before another patch. Evidence can justify a local repair; a rewrite is not presumed.

The existing map skill and two optional templates carry the same behavior. During resume or upgrade, conflicting generated procedure is reconciled in the active records, while owner choices, protected care, open failures and useful history survive. Unclear consequential authority still goes to the owner. This adds no installed file, skill, tool, dependency, compulsory record or review roster.

## Executed comparison

[Two offline cases](../devsuite/continuation/README.md) use a small Python packing-list app, outside the motivating product. The packing case has an old handoff pointing at heading punctuation while visible numbering marks the wrong saved item. The integrity case requires the storage repair to remain the next action because it prevents damaged private data being overwritten. Both include an explicitly generated obsolete v6 clause alongside current owner constraints.

Each case ran once with the preceding source (`27026f7`) and once with the revised method, using native Cursor Composer 2.5, identical prompts, a 120-second limit and two concurrent workers. The checker was outside each builder checkout. The unrepaired fixture failed both cases; separate positive controls passed. Returned implementations from both method versions were executed with fresh evaluator data, and their code and handoffs inspected. [Outputs, instruction hashes and reported usage](../docs/evidence/continuation-2026-10/results.json) are retained beside each returned implementation and handoff.

These four runs establish neither a quality advantage nor reliable adoption. Both methods repaired the requested job. Both left the generated v6 clause in active `product.md`; neither applied the reconciliation instruction to that record. The requests stated the desired job explicitly, so the comparison is weak evidence about choosing a destination from an ambiguous handoff. One run per arm cannot establish a speed or cost gain. The cases do not test visual quality, a complete consumer app or multi-contributor integration.

The observed omission remains a limitation of instruction-only distribution. Adoption therefore includes a concrete reconciliation of the motivating product's current handoff and map. That changes the next builder's actual input; it does not prove that the product has improved. Product work and paid/runtime allowances stay under their existing owner constraints.
