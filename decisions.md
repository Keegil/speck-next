**2026-08-17 · Releases: versioned surface, stateless upgrades, and the two upgrade roads.** How repos stay current, decided small: (1) `main` is the release line; any change to the installed surface (AGENTS.md, skills, `bin/`) bumps the version and gets a `vX.Y.Z` tag, so `npx github:Keegil/speck-next` installs latest and `#vX.Y.Z` pins. (2) The install marker records version *and* kernel commit, so `upgrade` reports exactly what span a repo crossed, and git in the target repo shows every changed line — no changelog corpus; the kernel's own plain-language git log is the changelog. (3) Upgrades are structurally safe because the method surface is stateless: it never touches the four product files, so upgrade = overwrite + one revertible commit, no markers, no catch-up ladders. The day a version changes the *file contract* (state.md's sections, product.md's expectations), that version's upgrader must carry the file migration itself — the marker's version is what it keys on; until then every upgrade is surface-only and free. (4) Old Speck v11 → Speck Next remains promise 5's deferred converter: the CLI refuses old-Speck repos loudly today, and the converter gets built as its own piece when the first real old-Speck repo (streb, brightstance, speilet, flyt) reaches a natural crossing point — against those real vintages as fixtures, with odd-old's distilled era knowledge as the quarry. Rejected: GitHub release artifacts and an exporter (the repo is the package — npm's git install ships it whole, and old Speck's exporter once shipped 18k lines of its own tests downstream); auto-upgrade hooks (an upgrade is a deliberate act with a diff the owner can see). First proof: the version fiction ended today — every install since day one said "1.0.0" while the surface moved through the whole campaign-feedback arc; v1.1.0 is the first true version, and Odd's upgrade to it is the first real span-crossing.

**2026-08-17 · The first real campaign's six lessons land — each in its smallest form, none as new machinery.** Odd's 30-round shaping campaign (verified against its primary artifacts, not the session's self-report) had to invent six disciplines the kernel didn't provide, and each now lives where it was missing: (1) the owner's words kept verbatim and append-only in the work file, the reference every review runs against (shape-product rule 10 — its scar: three refuters found non-verbatim quotes in the owner's mouth in product.md's first draft); (2) the round-trip rule extended to shaping (`AGENTS.md` — the owner's round-7 instinct was the method's own principle applied earlier than the method said; the wire reshaped a whole job when dinners turned out to have no evidence source); (3) drawings pressed against model and wire before the owner judges them (shape-product rule 11 — the journeys stress test found the campaign's largest defect); (4) shaping artifacts get the decorrelated refute pass *before the owner reads them*, judged against the owner record and the wire, never sibling documents (independent-review — and the census found the sharpest scar here: **every pass in the campaign was receiptless**, because the receipt law was scoped to reviews-that-run-products and the whole document stage fell in its blind spot; the extension closes the scope hole and states the receipt law applies unchanged); (5) a judging number is a hypothesis until it meets data, with honest denominators (attack playbook — the 0.60-floor and 431-av-609 scars); (6) where artifacts disagree, `product.md` and `decisions.md` win, and superseded artifacts say so at their top (`AGENTS.md` — cross-artifact contradiction was the campaign's biggest recurring defect class, and four superseded HTML decks still carry no marker, which is why the rule says *artifact*, not *document*). **2026-08-14 · AI-first means rebuilding the category, not decorating it — owner doctrine, refined.** The shaping skill's first AI-first cut asked "how would each surface work in 2126?" — which produces the same product with smarter screens. The owner's actual doctrine, now encoded as rule 2 and questions 9–13: reason from the job, the domain's first principles, and the user's real mental model; treat the category's inherited concepts as suspects (structures born of dumb software or physical constraints are fossils — deleted and rebuilt, never automated); take the best human who ever did this job as the interaction bar (asks, assumes out loud, takes corrections, remembers, adjusts); center the product on a living model of the user that does the work; and keep it honest with the collapse test — unplug the model, and a product that still works was never AI-first. **2026-08-13 · Structural investment is harness-owned at four points; judgment fills them — the anti-spaghetti design.** The owner's concern, and it's the classic agile failure: small loops that are each proven good can still stack jank, because stateless agent sessions don't accumulate the pain that triggers human refactoring, and nothing in a greedy loop rewards stopping. Decision: the harness owns *where pain is recorded, when it must be read, who calls it, and what repeated pain forces* — never *what the structure should be*. Concretely: (1) a strain ledger in `state.md` — working around instead of through anything writes a line, so pain survives between sessions; (2) shaping starts by reading it — twice-recorded strain becomes the next piece or is deferred visibly; (3) the structure verdict belongs to the independent reviewer (sound / straining / fighting), because the builder always has momentum and the party that wants to keep building never decides whether building pauses — two straining in a row, or one fighting, forces structural work; (4) predictable foundations are named at shaping time with the trigger that makes each due, and fire as ordinary pieces. Structural work is first-class: shaped and proven like a feature, proof = behavior unchanged and the strain gone. Considered instead: leaving it entirely to model/user judgment (rejected — the momentum conflict-of-interest is structural, same shape as self-review); mandatory periodic architecture reviews (rejected — cadence-based ceremony is how old Speck grew 183 findings with zero real defects); upfront foundation phases (rejected — old Speck's foundations were mostly documents about foundations; Odd had an architecture.md and no walking skeleton). Reopens if a real product accumulates spaghetti anyway — measured by refactor pieces repeatedly discovering strain no one recorded.

**2026-08-13 · Kernel development runs as an evolution loop with a train/test split.** The frozen contest stays the held-out exam — never iterated against, plantings secret. What was missing is the *search side*: a cheap development suite (tiny scored tasks on toy repos, plantings visible, runnable in minutes) that kernel changes are measured on between contests. Method changes follow candidate discipline: one mechanism per change, a falsifiable hypothesis with a predicted effect written in the work file, the measured result written back — which is also how promise 8's "predicted benefit, measured or retired" actually gets operationalized. Analysis reads real session transcripts and run logs, not summaries; and a change prompted by a dev-suite failure must pass the generality test — would it help across many unfamiliar tasks, or just this one? Pattern adapted from Stanford's Meta-Harness (github.com/stanford-iris-lab/meta-harness, arXiv:2603.28052), whose reference loop burns ~$500 per iteration — ours must cost pennies, so dev tasks stay pulse-sized. Considered instead: iterating directly against the contest (rejected — overfits the exam and breaks its integrity rules) and no quantitative loop at all, self-hosting friction only (rejected — friction finds usability problems but can't measure detection or cost regressions). Reopens if the dev suite and contest results ever diverge badly — that means the dev suite drifted from what matters.

**2026-08-13 · One method, many subjects.** The method surface (`AGENTS.md`, the skills, later the upgrader) is byte-identical in every repository it governs; only the four product files differ. This repository is not special — it's an ordinary Speck Next repo whose product happens to be the kernel, which is what makes self-hosting and installability the same thing rather than a conflict. Installing into a product repo means placing the method surface and creating (or converting) that product's four files; the kernel repo's own product files never ship anywhere. Product-specific standing guidance (stack, commands, conventions) belongs in the product's own files, which agents always read anyway — the method page stays identical everywhere; the exact seam gets settled when the upgrader is built. Considered instead: a special dev-mode method page for this repo (rejected — then we'd never be testing the real thing), and per-repo customized method pages (rejected — 5 diverging pages is the old upgrade treadmill reborn). Reopens if a product genuinely needs standing agent instructions that fit none of its four files. Editing `AGENTS.md` in this repo is always substantial work — it changes the governor — so it takes the full loop and independent review.
